# πCred Audit Registry

An on-chain registry of LLM smart-contract audits in the style of
[πCreds: Privately Inferred Credentials](https://arxiv.org/abs/2606.03771). A Python auditor runs inside a
Google Confidential Space TEE: it fetches a contract's bytecode and verified source from whitelisted sources,
has Claude audit it under a fixed prompt and rubric, and signs the result with a key whose address is bound
into the TEE's attestation token. `AuditRegistry.sol` verifies that attestation **on chain** (RS256 via the
`modexp` precompile) so that a stranger with only the registry address can check that a grade was produced by
an approved pipeline image, in a genuine TEE, over exactly the code it claims to cover.

Contract source is public, so privacy is not a goal. **Integrity of the audit is the only goal.**

## Layout

```
contracts/src/JwtVerifier.sol   RS256 JWT verification + structural JSON claim lookup (library, ~330 lines incl. docs)
contracts/src/AuditRegistry.sol signer registration, audit records, views (~260 lines)
contracts/script/Deploy.s.sol   constructor args from env: KIDS, MODULI, IMAGE_DIGESTS, OWNER
contracts/test/                 Foundry tests; fixtures generated by auditor/tests/make_fixtures.py
auditor/main.py                 FastAPI: POST /audit, GET /attestation, GET /config
auditor/fetch.py                oracle step: whitelisted RPC/Sourcify/Etherscan, proxy resolution, candidates, provenance
auditor/analyze.py              Claude tool loop, comment stripping, rubric, request/response hashing
auditor/credential.py           W3C VC assembly, EIP-712 signing, attestation request (real or MOCK_TEE)
auditor/config.py               τ: model, prompt, tool schemas, output schema, rubric, whitelist, RPC URLs, version
auditor/Dockerfile              Confidential Space image with launch policy
cli/                            request_audit, register_signer, submit_audit, verify_audit, jwks_keeper, export_snapshot
frontend/index.html             single-file viewer: reads the registry over JSON-RPC, re-verifies every record in the browser
```

## Quick start

```bash
cp .env.example .env            # fill ANTHROPIC_API_KEY, SEPOLIA_RPC_URL, DEPLOYER_PRIVATE_KEY (and ETHERSCAN_API_KEY)
python3 -m venv .venv && . .venv/bin/activate && pip install -r auditor/requirements.txt pyjwt

# 1. Fixtures (dev RSA key + tokens) and contract tests, with gas numbers printed
MOCK_TEE=1 python -m auditor.tests.make_fixtures
(cd contracts && forge test -vv)

# 2. Deploy: Google's two live JWKS keys + the dev key, and the mock image digest
set -a; . ./.env; set +a
eval "$(python cli/jwks_keeper.py --print-env --mock)"
(cd contracts && forge script script/Deploy.s.sol --rpc-url "$SEPOLIA_RPC_URL" --broadcast --private-key "$DEPLOYER_PRIVATE_KEY")
# write REGISTRY_ADDRESS / REGISTRY_DEPLOY_BLOCK into .env

# 3. Run the auditor locally with a mock attestation, then the full flow
MOCK_TEE=1 python -m auditor.main &
python cli/register_signer.py                                   # right after boot: tokens expire in ~1 h
python cli/request_audit.py --chain 11155111 --address 0x1c7D4B196Cb0C7B01d743Fbc6116a902379C7238
python cli/submit_audit.py --credential credentials/11155111-0x1c7d4b196cb0c7b01d743fbc6116a902379c7238.json
python cli/verify_audit.py --chain 11155111 --address 0x1c7D4B196Cb0C7B01d743Fbc6116a902379C7238 --credential credentials/...
python cli/jwks_keeper.py --loop 3600                           # keeps googleKeys current (see below)
```

For a real deployment, build and push `auditor/Dockerfile`, approve its digest with `setImageApproval`, launch it
in Confidential Space with `REGISTRY_CHAIN_ID`/`REGISTRY_ADDRESS`/`ANTHROPIC_API_KEY` as env, and run
`register_signer.py` within an hour of boot. Nothing else changes.

## Frontend

`frontend/index.html` is a single file with no build step. Serve it from anywhere (`python -m http.server -d frontend`)
and it reads the registry directly over JSON-RPC: `AuditSubmitted` and `SignerRegistered` events, then per record
it re-derives what a verifier would: current `EXTCODEHASH` against the audited `codeHash`, `reportHash` and
`dependenciesHash` recomputed from the emitted report, signer attestation and image approval, and the signer's
attestation JWT re-verified with WebCrypto (RS256) against the on-chain modulus, plus audience, nonce and `dbgstat`.
The connection panel takes any registry address, RPC and per-chain RPC map. `cli/export_snapshot.py` embeds a
chain snapshot into `frontend/snapshot.html` for hosting where the page cannot reach an RPC.

## What the credential binds

The on-chain `AuditRecord` (EIP-712, domain `AuditRegistry`/`1`/registry chain/registry address):

| field | meaning |
|---|---|
| `chainId`, `contractAddress`, `codeHash`, `blockNumber` | the audited code: `codeHash = keccak256(bytecode at blockNumber) = EXTCODEHASH` |
| `dependenciesHash` | `keccak256(abi.encode(Subject[]))` over the same tuple for every dependency the TEE fetched |
| `grade` (`A`..`F`), `score` (0..100) | rubric-enforced result |
| `configHash` | τ = `keccak256(canonical JSON of GET /config)`: model id, system prompt, tool schemas, output schema, rubric, source whitelist, RPC URLs, budgets, auditor version |
| `reportHash` | `keccak256(canonical JSON of credentialSubject)`; the full report is emitted in `AuditSubmitted` and must hash to it |

`credentialSubject` holds the structured audit (`grade`, `score`, `summary`, `findings[]`, `upgradeability`,
`confidence`, `scope`), the subject tuples, `notFetched` candidates with reasons, the SCAE check (grade with and
without comments/strings), the pipeline record (model id, sha256 of every Anthropic request and response body),
and provenance (RPC block hash, source provider URLs and body hashes, every tool call). Canonical JSON is
sorted keys, no whitespace, UTF-8.

## Attestation token: what the contract parses

Confidential Space OIDC tokens are RS256 JWTs signed by Google (issuer `https://confidentialcomputing.googleapis.com`,
JWKS at `https://www.googleapis.com/service_accounts/v1/metadata/jwk/signer@confidentialspace-sign.iam.gserviceaccount.com`).
The workload requests one over `/run/container_launcher/teeserver.sock` (`POST /v1/token`,
`{"audience", "token_type": "OIDC", "nonces": [...]}`; nonces are 10 to 74 bytes). Claims parsed on chain:

| claim | check |
|---|---|
| header `alg`, `kid` | `RS256`; `kid` selects `googleKeys[kid]` |
| `exp` | `> block.timestamp` |
| `aud` | `picreds-audit-registry:<chainId>:<registry address, lowercase>` (computed in the constructor, so a token cannot be replayed against another registry) |
| `dbgstat` | `disabled-since-boot` (debug images allow operator shell access) |
| `submods.container.image_digest` | `sha256:<64 hex>` in `approvedImages` |
| `eat_nonce` | `0x` + 40 lowercase hex = the signer address; Google documents it as string-or-array, both are accepted |

**Why a structural JSON walk and not a prefix search.** The token is Google-signed, but `registerSigner` must
also reject tokens from unapproved images, whose author controls `aud`, container `env` and `args`, and `aud`
precedes `submods` in the payload. A flat search for `"image_digest":"` could be spoofed by embedding that text
in `aud`. `JwtVerifier.claims` walks the object: keys are matched only at the requested nesting level and every
skipped value is skipped as a unit (strings with escapes, nested objects, scalars). The tests include
injection attempts through `aud` and `eat_nonce` against an unapproved image.

## Gas (Foundry, 2048-char token)

| operation | gas |
|---|---|
| `JwtVerifier.verify` (base64 decode, SHA-256, modexp, full 256-byte PKCS#1 compare) | 176,786 |
| `kid` + 5 top-level claims + `image_digest` lookup | 120,232 |
| library total | **297,018** |
| `registerSigner` (above + storage + event with full JWT) | 489,076 in tests (2,048-char mock token); 561,844 on Sepolia with the mock token; 759,900 on Sepolia with a real 3,296-char Google token (2,137-byte payload incl. `tdx` and `attester_tcb` claims) |
| `submitAudit` (small report) | 330,478 in tests; plus 16 gas per byte of report JSON |

Two passes over the token dominate: base64 decoding (about 75 gas per byte is the floor for any byte loop on the
EVM, done four characters per step with a lookup table) and the JSON walk (strings are skipped 32 bytes at a time).

A fresh VM (new signer `0x8De4Bb6F…46Be`, registered for 759,750 gas) audited six real deployments. The four
vulnerable ones are the original contracts of famous incidents, still on Ethereum mainnet with verified source;
the auditor had no hint of their history beyond the code and live state.

| contract | chain | grade | top finding (as reported by the TEE) |
|---|---|---|---|

| BeautyChain BEC `0xC5d105E6…793D` (2018) | mainnet | F / 5 | critical: integer overflow in `batchTransfer` allows unlimited minting |
| Rubixi `0xe8271920…20be` (2016) | mainnet | F / 5 | critical: misnamed constructor `DynamicPyramid` lets anyone become owner |
| Akutar `0xf42c318d…961d` (2022) | mainnet | F / 15 | critical: `claimProjectFunds` compares `refundProgress` with `totalBids`, locking proceeds forever |
| Multicall3 `0xcA11bde0…CA11` | Sepolia | A / 95 | low: ETH sent to non-value aggregate functions is stuck |
| Permit2 `0x00000000…8BA3` | Sepolia | A / 93 | low: `safeTransferFrom` to a codeless token succeeds silently |
| WETH9 `0xfFf99767…6B14` | Sepolia | A / 95 | low: approve front-running |
| Circle USDC `FiatTokenProxy` `0x1c7D4B19…7238` + `FiatTokenV2_2` | Sepolia | B / 80 | medium: proxy admin is an EOA with no timelock (re-audited from a third TEE session, signer `0x8a418313…be76`) |

Every record verified with `cli/verify_audit.py` (code unchanged, Google-signed attestation re-verified, report and
config hashes match). The frontend hides records whose signer was attested with a mock key, so only these seven
appear on the site.

Two things the real token confirmed. `submods.container.env` lists every container env var, including `tee-env-*` overrides,
so secrets must never be passed as env: the auditor reads its API keys from Secret Manager at boot through the VM's
service account. And the payload is about 500 bytes larger than the mock (extra `tdx` and `attester_tcb` claims), which
is where the extra registration gas goes.

## Trust assumptions

1. **TEE hardware and Google's launcher.** Intel TDX / AMD SEV-SNP isolation, and Confidential Space's measurement
   of the container image. Verifiers should also require `dbgstat`, which the contract does.
2. **Google's attestation signing keys.** `googleKeys` must hold Google's current JWKS. Only the registry owner can
   change it; a stale or malicious key set is detectable by anyone comparing against the live JWKS.
3. **The owner's approved-image list.** The owner can approve a malicious "auditor" image, but cannot register an
   arbitrary key for an approved image, and anyone can rebuild the Dockerfile and compare digests. A timelock on
   `setImageApproval` is the obvious hardening.
4. **Anthropic API.** Unlike the paper, inference runs on Anthropic's servers, not inside the TEE. The attestation
   covers the pipeline (what was fetched, what was sent, how the answer was constrained and graded) but **not the
   model execution**. The credential records the model id returned by the API and sha256 of every request and
   response body, which makes this trust assumption auditable with Anthropic's cooperation, not removable.
   Server-side refusal fallbacks are deliberately off: a model switch would break the model binding, so a refusal
   fails the audit instead.
5. **Sourcify / Etherscan.** Verified source is trusted to correspond to the bytecode (both verify by recompilation).
   The credential records which provider, match type, and response hash.
6. **RPC endpoint.** Trusted for bytecode and state at the pinned block. The URLs are part of τ, not operator env,
   so they are covered by `configHash`.

## Verification story

A stranger holding only the registry address runs `cli/verify_audit.py` (or does the same by hand):

1. `latestAudit(chainId, address)` returns the record; compare `record.codeHash` to the live `EXTCODEHASH`. A
   mismatch means the contract was upgraded or replaced after the audit.
2. `isAttestedSigner(record.signer)`; `signers(signer)` gives the image digest and the attestation hash.
3. Pull the `SignerRegistered` event for that signer: it carries the full JWT. Re-verify it offline against the
   on-chain `googleKeys[kid]` (or Google's live JWKS), check `aud`, and check the image digest matches an approved
   one and a reproducible build of the published auditor source.
4. Read `AuditSubmitted` for the record: the full report JSON must hash to `reportHash`. `GET /config` on any
   instance of the approved image (or the published config) must hash to `configHash`.
5. Optionally recompute `dependenciesHash` from the report's dependency tuples and check those contracts' code.

## SCAE / ACPP notes (paper §4)

The deployer controls the source text, so it is treated as untrusted data: it reaches the model only inside
delimited `<<<UNTRUSTED_CONTRACT_DATA ...>>>` blocks, the system prompt says comments, NatSpec, strings and
identifiers may be adversarial, and the audit runs twice, once with comments and string literal contents
stripped. A grade disagreement becomes a medium finding ("Possible auditor manipulation") and the worse grade is
reported. Identifiers are not renamed, since that would change what the model can read. ACPP (a malicious model
leaking through outputs) is out of scope here because privacy is not a goal; the model is fixed by `configHash`.

## Google key rotation

Google rotates the Confidential Space signing keys often (two are live at any time). `cli/jwks_keeper.py`
diffs the live JWKS against `GoogleKeySet`/`GoogleKeyRemoved` events and sends `setGoogleKey`/`removeGoogleKey`
as needed. Without a running keeper, `registerSigner` fails once the stored keys are stale; existing signers
are unaffected. Each rotation is two small transactions, negligible on an L2, a few dollars on mainnet.

## Known limitations

- Forced `tool_choice` is rejected by current Claude models, so the "forced final tool call" is implemented
  with structured outputs (`output_config.format`, schema-validated JSON) plus strict tools. Same guarantee.
- `scope` in the audit is computed by the pipeline from what was actually fetched, not by the model.
- Unverified source: the primary contract (or the implementation behind a proxy) without verified source caps
  the grade at C and the audit proceeds on bytecode. An unverified ordinary callee lowers confidence only.
- Source larger than 300k characters per contract is truncated with a visible marker; the model is told to
  lower confidence. Eight contracts, depth two, forty tool calls per audit.
- Slither is optional and not in the image by default; `run_slither` reports "not installed".
- Reproducible builds: the Dockerfile pins the base image by digest and dependencies by version, but a
  hash-locked requirements file and `SOURCE_DATE_EPOCH` discipline are still needed before two independent
  builds produce the same digest. The Google OIDC path also puts Google (not Intel/AMD directly) at the root.
- The registry has no timelock on `setImageApproval`, no multi-sig owner, and no way to revoke a signer; all are
  straightforward additions.
- Google's token key order is not documented; the structural parser does not depend on it, but the gas numbers
  above are for the mock token's layout, which mirrors Google's reference.
